### 复用要点（已写进 skill `ai-switch-route-diagnose`）

- 查账号健康要看 **`route_credential_models` 的逐模型失败**，账号级 `status='ok'` 完全可能是假的。
- **探针的 `model` 参数会被账号 `model_mappings` 改写**：映射里没有匹配的 `from` 时，
  请求会被改写成映射的 `to`（实测传 `gpt-6-astra-cc-format` 发出去的仍是 `claude-opus-5-5`）。
  所以「用探针验证另一个上游模型名」是无效实验，必须改映射。
- 排查第三方客户端报错，先读它的模型清单文件（`~/.workbuddy-ai/models.json`），
  能直接定位「走哪个平台、发哪个模型名、对应哪个账号」。

  `POST http://127.0.0.1:19527/api/route_pool_test_model`，body

## 补充（同日稍后）：用户复现并给出真错 —— `invalid codex request`

用户把 anyrouter 的 codex 账号重新启用后复现，日志里 12 条 400：

- `platform=codex`、`credential_name=anyrouter`、入口 `path=/v1/chat/completions`、
  `bridge=ChatToResponses`、`target_url=https://anyrouter.top/v1/responses`
- 上游 400 `{"error":{"message":"invalid codex request (request id: ...)","type":"new_api_error","code":"invalid_responses_request"}}`
- 客户端头里 `x-ide-name: WorkBuddy`、`x-ide-version: 5.6.2`、`x-domain: www.workbuddy.ai` → 确实是 WorkBuddy

**根因**：`src-tauri/src/services/route_protocol_bridge/chat_responses.rs::chat_request_to_responses`
（第 20–100 行）从不输出 `include` / `prompt_cache_key`。new-api 的 codex 通道要求请求必须带这两项，
缺任一项就 400。Codex CLI 自己会发这两项，所以 `ResponsesToResponses` 直通路径正常 —— 这解释了
「codex 可以、第三方客户端不行」。

**最小必需集（二分实测）**：`include` 必须**恰好** `["reasoning.encrypted_content"]`
（`[]` 或 `["reasoning.summary"]` 都不行），`prompt_cache_key` 必须**非空**，两者缺一不可；
`tools`/`reasoning`/`text`/`instructions`/`store`/`tool_choice`/`parallel_tool_calls` 都非必需。

**跨上游容忍度**：`JustDoWork/claude-opus-4-8`、`modelport/glm-5.3` 对加不加这两字段都是 200
（AgentRouterL 因 quota 用尽，未得出结论）→ 无条件补上对已验证上游无害，但属跨 provider 行为变更，
**已向用户提出两种方案待其选择**（无条件补 / 新增账号级开关），尚未改代码。

**新掌握的通用手法**：用 ai-switch 自己的 codex 代理入口做形状二分，不必直连上游 ——
`POST http://127.0.0.1:19527/v1/responses`，Bearer 用 `route_proxy_keys` 里 platform=codex 的 key，
`model` 写 `<账号名>/<上游模型名>`（账号必须 enabled）。

## 已实现：方案 1（用户选定），改动 3 个文件

共享实现收敛在 `src-tauri/src/services/route_protocol_bridge/common.rs`（新增 ~88 行）：

- 新增常量 `CODEX_ENCRYPTED_REASONING_INCLUDE = "reasoning.encrypted_content"`，带注释说明
  New API Codex 通道要求 `include` **恰好**是这一个值 + `prompt_cache_key` 非空。
- 新增 `ensure_codex_request_shape(&mut Map<String, Value>)`：**只在客户端没给时补** ——
  已有非空 `include` / `prompt_cache_key` 一律原样保留（key 是上游 prompt cache 的分片键，
  覆盖它等于废掉客户端自己的缓存命中）。`include` 是空数组或缺失才补；`prompt_cache_key` 是
  空串/非字符串/缺失才补。
- 辅助 `fn prompt_cache_key(object) -> String`：扫 `messages` **和** `input` 两个字段
  （chat 方言用前者、Responses 方言用后者）找第一条 `role=="user"` 的轮次，
  `serde_json::to_string` 后 SHA-256 十六进制；没有 user 轮次则退化为整包 hash。
  **刻意不用 `Uuid::new_v4()`**（探针那种写法）——随机 key 每轮都变等于放弃上游 prompt cache，
  稳定 key 才能让同一会话的后续轮次命中缓存。

挂载点两处（都调用共享函数）：

- `chat_responses.rs::chat_request_to_responses` 末尾（`ChatToResponses`，即 WorkBuddy 走的那条路）。
- `responses_responses.rs::responses_request_to_responses` 里 `clear_unstored_reasoning_ids` 之后
  （`ResponsesToResponses`，用户后续追加要求「也得缺失时自动补」）。

**关键实测结论：`include` 只能替换、不能合并。** 客户端已给 `include:["reasoning.summary"]` 时，
合并成 `["reasoning.summary","reasoning.encrypted_content"]` 能过形状门（不是 400）但**稳定 520**，
单一值稳定 200 → 所以策略是「空就补成单一值，非空就原样留」。

测试：

- `common.rs` 无独立测试模块，由两个调用方覆盖。
- `chat_responses.rs`：`the_bridged_body_carries_the_codex_shape_new_api_requires` /
  `the_prompt_cache_key_is_stable_across_the_turns_of_one_conversation` /
  `a_request_without_a_user_turn_still_gets_a_prompt_cache_key`。
- `responses_responses.rs`：`supplies_the_codex_shape_a_bare_responses_client_cannot_send` /
  `leaves_a_clients_own_codex_shape_untouched` / `derives_the_same_key_for_the_same_opening_turn`。
- ⚠️ **必须同步改 `mod.rs::leaves_other_protocol_pairs_unbridged`**：它原先断言
  codex+`/v1/responses` 直通路径「body 逐字节不变」，本次改动后必然失败。已改为
  「客户端原字段全部保留 + `include` / `prompt_cache_key` 到位」。
- 验证：`cargo test --lib route_protocol_bridge` → **225 passed / 0 failed**；

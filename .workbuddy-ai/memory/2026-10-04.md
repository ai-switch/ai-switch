### 本次踩到的点

1. **更新日志提交用 `--allow-empty`**：AGENTS.md 说「使用同一份双语更新日志作为 Git
   提交信息」，但该提交不携带文件改动，普通 `git commit` 会因空暂存区被拒。上一版
   v0.10.9 的 Release 提交是连带改文件的，这次没有文件要改，故用空提交。
2. **Cargo.lock 用 `cargo update --package ai-switch --offline` 更新**，不要手改。
   它在 git diff 里显示为二进制（因 `.gitattributes` 的 eol 规则），但加 `--text`
   可确认只改了 `version` 一行，124 个依赖未动。
3. **版本文件行尾各不相同**：`tauri.conf.json` 是 CRLF（76 行全 CRLF），
   `package.json` / `Cargo.toml` 是 LF。逐文件精确替换，勿整体归一化——
   `.gitattributes` 的注释明确警告过 `* text=auto` 会重写无关文件。
4. **`node -e` 里调`spawnSync` 也会 EBUSY**，包括 `spawnSync('git', ...)`。
   要在 node 里跑 git/子进程得注意这点；纯文本处理用 node 可以，起进程不行。
5. 更新日志格式已核验：标题 `Release v0.10.10`，第 7 行是唯一的长连字符分隔线
   （**29 个**，与 v0.10.9 一致），全文无其他 12+ 连续 `-`/`*`/`_`。

## 修复：用量统计里的「未经代理」行（Codex 侧 join key 丢失）

用户问「为什么有未经代理，服务器有记录但没绑到服务商」。查代码 + 只读查本机
`~/.ai-switch/ai-switch.db` 后定位并修复，改动仅一个文件：
`src-tauri/src/services/session_usage_service.rs`。

### 机制（`src-tauri/src/services/usage_overview_service.rs`）

- 统计页把两侧合并：代理侧 `usage_events`（`list_request_events`）+ 本机会话文件
  （`session_usage_service`）。
- join key 是**上游响应 ID**（`upstream_response_id` ↔ 会话里的 `response_id`）。
  相等 → `matched`；失败 → `session_only`。
- `NO_ACCOUNT_LABEL = "未经代理"`（489 行）只在账号与账号 ID **都为空**时出现，
  `session_only_row()` 硬编码 `account_id: None, account_name: None`。
- 前端两处兜底：`UsageOverviewPanel.tsx:311`（详情）、`:392`（列表）。

### 关键判断：标签的含义

「未经代理」≠「这条请求没走代理」，而是「这一行没认领到账号」。实测代理侧
101,087 行 request 的
`COALESCE(display_name, json_extract(metadata_json,'$.route_credential_name'))`
**无一行为空**（230 行账号已删的仍从 metadata 兜底拿到名字），所以代理行永远
不会显示这个标签 —— 它 100% 来自会话侧未配对的行。

### 真正的根因（第一版诊断错了，已纠正）

Codex 新版（cli_version 0.154.0，originator `@agentclientprotocol/codex-acp`）
的 reasoning item 长这样：

```json
{"type":"response_item","payload":{"type":"reasoning",
 "id":"e34d9c8c-2549-42f2-b07f-ddb454ed7a6a",
 "encrypted_content":"c96a18b7-aaa4-4a74-b482-b2caddb0faab-0"}}
```

`id` 是**客户端本地生成的 v4 uuid，无任何前缀** → `codex_assistant_response_id`
返回 None。**上游 response id 在 `encrypted_content` 里**，尾部 `-<n>` 是同一
响应有多个 reasoning item 时的序号，要去掉。

我第一版猜「裸 UUID 就是上游 id，直接当 key 用」，实测**0/430 命中**代理侧，
是错的 —— 这些 v4 是客户端自己造的，与上游无关。是对同一会话按时间窗反查代理侧
记录、逐字节比对才定位到 `encrypted_content`。

数据：近 14 天 reasoning 的 `encrypted_content` 里 929 个 uuid 形态值，
436 个（46.9%）在代理侧能命中。前缀形态仍有效（`msg_` 去前缀 727/800 命中）。

### 修复内容

`codex_assistant_response_id` 改为两级：先试原有前缀形态（优先，它是上游自己铸的
id，无需形状校验）；前缀缺失且 `type == "reasoning"` 时，回退读
`encrypted_content` 的 uuid 头。新增 `encrypted_content_response_id()` 与
`UUID_LEN`，用 `str::get(..36)` 而非索引以避开多字节字符 panic；校验 36 字符
uuid 形状（位置 8/13/18/23 为 `-`，其余小写十六进制）+ 尾部只能是可选 `-<n>`。
这道形状校验顺带排掉该字段的其他产出者：代理自己的 `ai-switch-anthropic:…`
标记、以及未走本app 的 provider 返回的 base64 blob。

### 效果与残留（近14 天 Codex 计费行 3518 行）

- 修复后能取到 response_id：**3026 行（86.0%）**，原为 2098（59.9%）。
- 残留 492 行无 id，**464 行集中在单个会话文件**（09-29 那个 5005 行的 rollout）。
- 该文件 291 条 reasoning 带标准 uuid、377 条是 **16 字符 hex（MongoDB ObjectId 形态）**，
  且 `encrypted_content` 为 `null`。
- 但这批 id 在代理侧 **0/377 命中**；抽样一个 id 在全库（含 metadata 预览）出现 0 次。
  该时间窗代理行的上游模型与该会话对不上。
- **结论：这 464 行是本来就没走本机代理的会话**（`~/.codex/config.toml` 里另有指向
  第三方站点的 provider，绕过了本机代理）。「未经代理」在这里是**如实反映**，
  不是缺陷。剩余 28 行散落在 5 个文件里，同样是无 id 可配的边缘 turn。

### 关于 `item_completed`（结论：不修）

我上一版把「解析器只找含 `response_item` 的行」列为遗留盲区。实测后**这个盲区
不存在**：

- `item_completed` 的 item 放在 `payload.item`，是 `response_item` 的**重复副本**
  （同一 item 记两次，时序上 `item_completed` 在前、`response_item` 紧随）。
- **只有 `response_item` 那份带 `encrypted_content`**（291 vs 0）——而那里正是
  上游 id 所在。所以读 `item_completed` 拿不到任何额外信息。
- 实测净增 **0**：41 个文件、3518 个计费行，加它前后都是 3026。
- 已在 `parse_codex_file` 的前置过滤处加注释说明为何**故意不**加它，免得后人
  再踩一遍。

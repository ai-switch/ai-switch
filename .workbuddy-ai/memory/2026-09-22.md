### ⚠️ `ultra→max` 映射存疑（用户质疑后复核查证，结论未定）
我原先写的「ZCode 最高档叫 max，对应目录 ultra」**前半句有据、后半句是推断，站不住**：

- **有据**：真机 `~/.zcode/v2/config.json` 里 10 个 `reasoning` 块**完全一致**
  ——`variants: ["low","max","high"]`、`defaultVariant:"max"`、`enabled:true`，
  但全部属于 5 个 **`builtin:`** 提供商（zai / bigmodel 系列），**没有一个是我们写的**。
  另在 Electron 本地存储 `Roaming/ZCode/session/Local Storage/leveldb/000004.log`
  里存着 `"reasoningLevel":"max"`（18 处，模型 `AgentRouterGithub/glm-5.3`、
  provider 结尾 `tch-codex` 即 `ai-switch-codex`）。
- **站不住**：builtin 档位只有 **low / max / high 三档，连 `medium` 都没有**——
  说明这只是那几家内置提供商的用词，不能推出「自定义提供商也必须叫 max」，
  更不能推出 `ultra` 非法。`deepseek_harness.rs:127` 的 `ultra→max` 是**另一个客户端**
  的约定，拿来类推 ZCode 属于弱证据。用户指出 **ZCode 设置里可自定义推理档位**，
  若 `variants` 是自由字符串数组，改名就是多余且会篡改用户配置。
- 排查手法记档：解析多行 JSON 别用 `grep -o '"variants":\[[^]]*\]'`（多行数组匹配不到），
  用 python 遍历 `provider.*.models.*.reasoning` 聚合 uniq。

**已定（用户选）**：**原样透传，去掉 `ultra→max` 改名**。理由：ZCode 支持自定义推理档位，
`variants` 是自由字符串数组，改名会篡改用户在目录里配的档位名、与 AI Switch 显示不一致。
结论：ZCode 内置的 `low/high/max` 只是那几家内置提供商的用词，**不是** ZCode 的强制枚举，
别再拿它去反推映射。

### ⚠️ 新坑：`sed -i` 同样会把 tauri.conf.json 的 CRLF 改成 LF
旧笔记只写了「编辑工具写文件会 CRLF→LF」，这次证实 **Git Bash 的 `sed -i` 也会**

`git diff --numstat` 从 `1 1` 爆成 `76 76`。

`w/crlf` + numstat 回到 `1 1` + `tr -dc '\r' < f | wc -c` = 76（=行数）。
→ 结论：**改 tauri.conf.json 一律走 sed + 事后补 CR**，别用编辑工具，也别以为 sed 安全。

另注一个容易误判的现象：`reset --mixed HEAD~1` 撤掉 Release 提交后 HEAD 的版本是

### macOS Intel 前端测试失败的定位结论（就是上面那个卡点）
跑全量 vitest 取耗时：`vitest run --reporter=json --outputFile=<file>`
（2m16s / 868 用例全过），再解析 `testResults[].assertionResults[].duration`：
- 本机 Windows 最慢 **2163ms**（AccountsScreen saves the Claude subagent and fallback mappings）
- >=2000ms **4 个**，>=3000ms **0 个**；最慢的一批几乎全在 `tests/AccountsScreen.test.tsx`
- **2089ms 的 `accepts a context window typed by hand instead of a preset` 正是本次新增的
  用例** —— `git diff v0.10.2 HEAD -- tests/` 只动了 AccountsScreen.test.tsx(+29) 和
  codexModelCapability.test.ts(+11/-1)

→ 结论：`vitest.config.ts` **没有设 `testTimeout`**（默认 5000ms）。本机最慢已 2.16s，
而 `macos-15-intel` 是 x86_64 runner、比本机慢 2–3 倍 → 越过 5s 超时。
这正好解释「Linux / Windows / macOS ARM 都过、只有 Intel 挂」。
→ 修法：给 `vitest.config.ts` 的 `test` 段加 `testTimeout`（建议 15000；正常用例不受影响，
只在真超时时才多等）。

**注意 re-run 不生效**：GitHub 的 "Re-run failed jobs" 用的是**原 run 的 commit**
（3620c567），不会拉新代码。所以改完必须重新触发（删远程 tag 重推，或发新版本）。

## 排查「模型测试请求报错」的方法（anyrouter / Claude tab 520）
- 测试请求的结果**不进** `~/.ai-switch/logs/route-proxy-live-log.jsonl`——那只是代理流量
  日志（实测 anyrouter 在里面 0 条）。结果存在数据库：
  `route_credentials.last_failure_kind / last_failure_message / last_failure_response_json`，
  以及**按模型细分**的 `route_credential_models`（注意列名是 `route_credential_id`，
  不是 `credential_id`）——后者信息量大得多，能看到每个模型各自的错误码。
- 库位置：`~/.ai-switch/ai-switch.db`（release，运行中可只读打开
  `sqlite3.connect('file:...?mode=ro', uri=True)`）/ `ai-switch-dev.db`（dev）。
  key 在 `secret_payload_json.api_key`；`config_json.api_key_field` 决定发
  Bearer（`ANTHROPIC_AUTH_TOKEN`）还是 `x-api-key`（`ANTHROPIC_API_KEY`）。
- 请求构造（`route_model_test_service.rs`）：claude 平台固定 `/v1/messages` +
  `anthropic_probe_body`（带 Claude Code 的 `system` 与 `metadata.user_id` 过中继门禁）；
  **codex 平台固定 `/responses`**（不带 `/v1`），再经协议桥转 anthropic。
  `CLAUDE_CODE_SYSTEM_PROMPT` 只有一句话，不是体积问题。
- ⚠️ **本机无法直连 anyrouter.top 实测**：出网必须走 `https_proxy=127.0.0.1:65243`，
  该代理在 TLS 握手阶段就 `SEC_E_ILLEGAL_MESSAGE` 断开；`--noproxy '*'` 直连则
  HTTP_CODE=000；Python urllib 同样 `SSLV3_ALERT_HANDSHAKE_FAILURE`。
  → 这类问题只能靠库里存的失败信息推断，**别浪费时间尝试复现**。
- 本次结论：anyrouter 的 6 个 claude 别名**全部**映射到 `claude-fable-5-1`，该模型走
  `/v1/messages` = 520、走 `/responses` = 400，而同账号 `gpt-6-astra` 能返回正常的中文
  业务错误（"负载已经达到上限"）→ 是 `claude-fable-5-1` 这个 custom 模型在 anyrouter 侧
  失效，**不是** AI Switch 的请求构造问题（其他中继账号都拿得到具体错误文本，
  如额度不足 / No available channel / 403 / 405）。

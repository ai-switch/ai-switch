## issue #17: 非正常关机后 ai-switch.db 页级损坏
- 根因：生产 `create_pool`（database/mod.rs）只设 `create_if_missing + foreign_keys`，**没启用 WAL**，跑在默认 DELETE 回滚日志模式。断电时回滚日志已写但数据页未完整落盘 → 页级损坏（2nd reference to page / rowid out of order）。讽刺的是 saas/billing/tests.rs:320 的测试库正确用了 `.journal_mode(Wal).busy_timeout(10s)`，主库却没。
- sqlx 0.8.6 API 确认（看 ~/.cargo/registry/src/index.crates.io-*/sqlx-sqlite-0.8.6/src/options/）：`SqliteJournalMode::Wal`、`SqliteSynchronous::Normal`（注意枚举名叫 `SqliteSynchronous` 不是 `SqliteSynchronousMode`）、`busy_timeout(Duration)`。默认 busy_timeout 已是 5s（options/mod.rs:201）。`journal_mode`/`synchronous` 走 `pragma()` 每连接都发。
- 修复分两层（都在 src-tauri/src/database/mod.rs）：
  1. **配置层**：`create_pool` 加 `.journal_mode(Wal).synchronous(Normal).busy_timeout(5s)`。WAL 写前先落 -wal sidecar，checkpoint 才合并主库 → 断电不污染主库页。NORMAL 是 SQLite 文档对 WAL 标注的 corruption-safe 配对。
  2. **启动自愈层**：`open_migrated_pool` 在 `run_migrations` 前加 `check_integrity`（`PRAGMA quick_check`）；检测到损坏走 `recover_from_corruption` → `salvage_database`（ATTACH 坏库、按表 `INSERT INTO main.t SELECT * FROM src.t`、坏表跳过并记录）→ 迁移 salvage → `park_corrupt_database`（搬到 backups/ 加 `.corrupt-{stamp}` 标记 + 写说明 txt，**不用** `.migration-conflict-` 标记以免被 restore 逻辑当恢复候选）→ 提升 salvage 为主库。salvage 全失败则保留坏库原位 + 报致命错（不删数据）。
- 测试（recovery_tests 新增 4 个）：WAL+NORMAL 验证、quick_check 健库 ok、salvage 拷贝 schema+数据+迁移账本、端到端损坏恢复（200 行 usage_events + 1 账号 → checkpoint TRUNCATE → 删 -wal/-shm → 用 0xFF 覆盖文件 3/4 处一整页 → 断言账号存活 + 坏库被 park）。
- ATTACH 坏库用单连接 `SqliteConnection`（非 pool，因 ATTACH 是 per-connection）；`Connection` trait 要 `use sqlx::Connection;` 才能用 `connect_with`/`close`（close 消费 self）。
- 待验证：编译 + 测试结果（cargo test --lib recovery_tests 后台跑）。

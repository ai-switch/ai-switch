## usage_events 请求统计提列（方案1+2，账号列表性能）
- 背景：账号列表 `PAGE_SELECT`/`list_by_platform` 每 join 行都 `json_extract(metadata_json,'$.success'|'$.duration_ms')`，而同一 `metadata_json` 还塞着（压缩后的）`response_body`/`response_body_br` 预览；`usage_events` 从不清理 → 历史越长列表越慢。真正杀手是「流水表无限增长 × 全量聚合 × 每行解析被大字段撑大的 JSON」。
- 改法（纯增量、不动 response_body 存储）：
  - 新迁移 `migrations/202609270001_usage_request_stats_columns.sql`：`ADD COLUMN success INTEGER` + `duration_ms INTEGER`；用 `json_extract` 回填历史（LIKE 守卫）；加索引 `idx_usage_events_request_stats (route_credential_id, source_label, metric_type, created_at)`。
  - checksum 追加进 `src/database/migration_checksums.txt`（SHA-384，用 python 算：`hashlib.sha384(open(f,'rb').read())`，确认无 CR）。**新迁移不加进 manifest 会导致 `shipped_migrations_keep_their_original_checksums` 断言 unpinned 失败**。
  - 写入端提列：`route_pool_repository.rs` 新增自由函数 `request_stat_columns(metadata_json)->(Option<i64> success01, Option<i64> duration_ms)`（parse 失败/缺键→None，success 存 1/0）。`insert_request_event` 和 `insert_usage_event` 两处 INSERT 都补 `success, duration_ms` 两列绑定。
  - 读取端 SQL：`route_credential_repository.rs` 的 `PAGE_SELECT` 与 `list_by_platform` 把 `json_extract(...$.success)`→`ue.success=1`、`json_extract(...$.duration_ms)`→`duration_ms` 列。
  - 文档：`docs-site/docs/{,en/}guide/usage-stats.md` 迁移表 + 「账号列表上的成功率」段同步（含为什么提列、索引）。
- 语义等价校验（真 SQLite `json_extract`，python 验证）：`{"success":true}`→1、`false`→0、`{"success":1}`→1/duration NULL、无键→NULL、非法 JSON→NULL。与聚合把 NULL 当「非成功」的老口径一致。
- 踩坑：`list_includes_request_success_statistics` 测试走的是 `insert_usage_event`（不是 `insert_request_event`），只改后者会让该测试 success_count 归零 → 两个 INSERT 都要提列。
- 验证：`route_pool_repository` 21 passed（含新加 2 个提列/NULL 测试）、`route_credential_repository` 41 passed、`route_pool_service` 17 passed、`migration_checksum` 3 passed、`check --bin ai-switch-server --features standalone-server` EXIT 0。
- 未做（可选后续）：response_body 仍在 metadata_json 内（方案「拆 body 到独立表」未做，用户只要 1+2）；`usage_events` 保留/清理策略仍无。

## 清理缓存功能（回填 + 按时间清 response_body + 设置页 UI）
- 需求：设置里给「清理缓存」，用户选清理多久之前的 response_body/response_body_br。前置结论：统计已提列（见上），删 body 不影响任何数字。
- **前置回填服务** `services/usage_response_id_backfill_service.rs`：把旧行藏在 body 预览里的 `upstream_response_id` 抢救进独立列（列早在 `202609020003` 就有，问题是旧行为 NULL、值只在 body）。选 `metric_type='request' AND upstream_response_id IS NULL AND (LIKE response_body/br)`，解 body（`brotli_codec::decode_stored_text` 认两种键）→ `upstream_response_id::extract_upstream_response_id` → UPDATE 列。分批200/独立事务/yield/幂等。`backfill_upstream_response_ids_after_startup(pool)` **交出 future**，desktop.rs（`tauri::async_runtime::spawn`）+ server.rs（`tokio::spawn`）两处挂载，START_DELAY 10s。5 单测过。
- **清理服务** `services/usage_response_body_cleanup_service.rs`：`clear_response_bodies_before(pool, cutoff_rfc3339)` 删 `created_at <= cutoff` 的 request 行里两个键（`json` 对象 remove 两键后重写 metadata_json，不删行）。分批/事务/yield/幂等。返回 `CleanupSummary{cleared, freed_metadata_bytes}`。4 单测过。RFC3339 时间戳字符串**按字典序比较**（定宽 UTC 格式，正确）。
- **core 层** `core/usage_history.rs`：`clear_response_bodies_core(pool, older_than_days)` → `cutoff = (Utc::now()-Duration::days(days)).to_rfc3339()`，负数 clamp 到 0（=全部）。返回 `ResponseBodyCleanup{cleared_rows, freed_metadata_bytes, reclaimable_bytes}`（含清理后 freelist 供 UI 提示可 VACUUM）。
- **命令** `commands/usage_stats_commands.rs`：`clear_usage_response_bodies`（`rename_all="snake_case"`，参数 `older_than_days`）。desktop.rs `invoke_handler` + import 注册；web `handlers/mod.rs` 派发 + **加进 `is_sensitive_command`**（bulk mutation 不该让远程浏览器触发）；web 端参数用 `optional_i64_arg(...,"older_than_days").unwrap_or(0)`。
- **前端**：`client.ts` `clearUsageResponseBodies(olderThanDays)`；`types.ts` `ResponseBodyCleanup`（camelCase：clearedRows/freedMetadataBytes/reclaimableBytes，与 serde `rename_all="camelCase"` 对齐）；`components/settings/usage-storage-settings.tsx` 加清理区块（select 7/30/90/0 天 + 清理按钮 + 结果提示），清理成功回写 STORAGE_QUERY_KEY 的 reclaimable_bytes；i18n 中英各加 `settings.storage.cleanup.*`（含 range.7/30/90/0）。
- 文档：`usage-stats.md` 中英各加「清理缓存的响应内容」段（讲提列后删 body 不影响统计、先回填 upstream_response_id、删≠文件变小需 VACUUM）。

## ⚠️ Rust 构建 E0107（schemars/indexmap）根因：沙箱里管道建不出来

- 症状：`cargo test --lib` / `cargo check` 挂在 `schemars 0.8.22`：
  `error[E0107] struct takes 3 generic arguments but 2 … indexmap::IndexMap<K, V>`（指向 `indexmap-1.9.3/src/map.rs:76`）。
- **根因（已定位到机制）**：在 WorkBuddy 沙箱内，`std::process::Command` 带 `piped()` stdio 的 spawn **必失败**：
  `os error 231`（ERROR_PIPE_BUSY，「所有的管道范例都在使用中」）。`Stdio::null()` 正常、与子进程是 `rustc` 还是 `cmd` 无关 → 是 Rust 在 Windows 上用命名管道实现匿名管道这一步被沙箱挡了。
  → autocfg 的 `probe_sysroot_crate("std")` 返回 false → indexmap 1.9.3 的 build.rs 不 emit `has_std` → `IndexMap<K,V,S>` 的 `S` 没有默认值（`RandomState`）→ schemars `preserve_order` 的 `Map<K,V> = indexmap::IndexMap<K,V>` 报 E0107。
- **证据**：最小工程（`Cargo.toml` 只依赖 autocfg，build.rs 里打印 `probe_sysroot_crate("std")` + 自己 spawn `rustc`）：
  - 沙箱内：`sandboxed=true probe_std=false piped_ok=0/3 err="os error 231"`
  - 沙箱外（同一 shell，仅沙箱状态不同）：`sandboxed=false probe_std=true piped_ok=3/3`
  - 仓库里 indexmap 构建脚本缓存的 `stderr` 就写着 `warning: autocfg could not probe for \`std\``。
- **`RUSTC_WRAPPER=sccache` 与此无关**（此前一版记录把它当根因，是错的：它只是和「这次调用是否被沙箱拦」巧合相关）。
- 沙箱状态自检：`env | grep -q LSBOX_SHMEM_NAME`（PowerShell 通道同样在沙箱内）。`dangerouslyDisableSandbox: true` 不一定生效。
- **cargo 会缓存并「重放」构建脚本输出**：build.rs 只声明了 `rerun-if-changed=build.rs`，改环境变量不会让它重跑 → 一旦缓存了坏结果就**一直**是坏的，必须 `cargo clean -p indexmap`。
- **解法**：
  1. 优先：`cargo clean -p indexmap` + 在**非沙箱**环境重建（用户自己终端里天然满足）。
  2. 拿不到非沙箱窗口时的一次性绕过：`cargo clean -p indexmap && CARGO_FEATURE_STD=1 cargo check --lib`。
     indexmap 的 build.rs 是 `match env::var_os("CARGO_FEATURE_STD") { Some(_) => autocfg::emit("has_std"), None => autocfg::new().emit_sysroot_crate("std") }` → 设了这个变量就**跳过探测**直接声明 `has_std`（windows-msvc 上这个值本来就是对的）。写进缓存的输出是健康的，之后**普通** `cargo check`/`cargo test` 会直接复用（已验证：output 的 mtime 未变、plain check 30s 通过），不需要任何仓库改动或 registry 补丁。
- 附带：`docs:build` 在本会话会被 WorkBuddy 的 node safe-delete shim 拦（vite 清空 `docs-site/docs/.vitepress/dist/assets` 137 个文件 > 阈值 50）→ 加 `CODEBUDDY_SAFE_DELETE_ENABLED=0` 可跑通。

1. 请求 `input` 里 `function_call` / `function_call_output` 的 `call_id` 是**空字符串 `""`**（不是字段缺失）。4 个工具项全空，2 个并行 `exec_command`。

3. 发出侧 bug：`responses_chat.rs:662-664`
   ```rust
   if let Some(id) = value.get("id").and_then(Value::as_str) { tool.call_id = id.to_string(); }
   ```
   流式每个 delta 分片**无条件覆盖** `call_id`，上游分片带 `"id":""` 就把已拿到的真 id 覆盖成空串。同文件 `:652` 的 `unwrap_or("call_ai_switch")` 也只兜「字段缺失」不兜「空串」。同类缺口还有 `responses_chat.rs:918`、`responses_claude.rs:1651`；而 `claude_chat.rs:430`、`claude_responses.rs:394` 是**正确写法**（`if tool.id.is_empty() { "call_ai_switch" } else { ... }`）。
4. 重放侧 bug：`responses_responses.rs::repair_input_item_call_id` 与 `responses_chat.rs::tool_result_call_id` 都只在 **`pending_call_ids.len() == 1`** 时补 `call_id`（`eb85fb0 2026-09-14 fix(bridge): match missing tool call IDs precisely` 故意做的保守策略）。本例有 **2 个并行调用** → 不补。且 `responses_responses.rs` **从不**给 `function_call` 项补 `call_id`，所以 StepFun 的 `function_call call_id is required` 在直通桥下**永远无法满足**。

**id 形态的判据（很有用）**：`msg_`/`rs_`/`fc_` 是**代理**发出的（`session_usage_service.rs:806-811` 注释），`fco_` 才是客户端的；`fc_<response_id>_<index>` 唯一由 `responses_chat.rs:648`（流式）产生（`responses_claude.rs:1690` 的 `rs_` 带数字 block 后缀，可据此区分）。本例 `rs_<resp>` 无数字后缀 → 确认是 **chat 桥**。

**影响面**：按 `session_id` 汇总 —— `01a0d21d-227f-7823-a685-77d4ab0ef924` **137 个请求全带空 call_id、0 成功**；其余 1076 个请求（无该 session 标记）0 个空 call_id、764 成功。即**一个坏轮次污染整个会话**，因为 Codex 每轮都全量重放历史。

**规避**：弃用那个 Codex 会话即可（坏轮次只在那一个 rollout 文件里）。

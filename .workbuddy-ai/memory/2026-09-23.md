### 数据库膨胀根因：`response_body` 不是 `instructions`（同日 10:38 诊断）

用户问「是不是存了请求日志 / `instructions` 字段导致重复系统提示词」。**结论：不是 instructions，
是 `metadata_json` 里的 `response_body`，而且它是设计如此、且从不清理。**

`~/.ai-switch/ai-switch.db` = **337 MB**（全库 86204 页，`freelist=0` 即无空洞可回收），
其中 `usage_events` **92,673 行**（全部 2026-09 一个月内，`metric_type` 全是 `request`）。

各列总字节（按 `length()` 估算，text 列合计 232.6 MiB）：

| 列 | 合计 | 平均/行 |
| --- | --- | --- |
| **`metadata_json`** | **229.6 MiB** | **2477 B** |
| `id` | 3.3 MB | 36 |
| `route_credential_id` | 3.3 MB | 36 |
| `created_at` | 3.2 MB | 35 |
| `upstream_response_id` | 2.3 MB | 37.5 |
| 其余（`source_label`/`metric_type`/`unit` 等） | ~2.1 MB | — |

`metadata_json` 内部（2 万行样本）：**`response_body` 一项 161.2 MiB / 90,696 行**，
平均 1864 字符、**最大 16,384 字符** —— 正好是常量上限，说明它在**系统性地存满**。
其余键（`path`/`status`/`success`/`duration_ms`/`trace_id`/`target_url`/`requested_model`/
`upstream_model` 等）加起来不到 4 MiB。

真正吃空间的机制（`route_proxy_service.rs`）：
- `fn route_proxy_response_body_metadata()`：成功截 **2 KiB**（`ROUTE_PROXY_SUCCESS_BODY_LIMIT`），
  失败截 **16 KiB**（`ROUTE_PROXY_RESPONSE_BODY_LIMIT`），截完以 lossy UTF-8 原样塞进 `metadata_json`。
- 该步骤上方的注释**自己写着** `usage_events, which is never pruned` —— 设计上就不清理。
- 实测分布与此吻合：`success=1` 69,696 行 / 179.8 MiB（均 2705 B）；
  `success=0` 22,977 行 / 39.2 MiB（均 1788 B）。
- 存的是 **SSE 原始流**（`event: response.created\ndata: {...}` 逐块），不是最终文本，
  所以单条能顶满 16 KiB。`route_model_test_service.rs:1962` 也往同一个 key 写。

**为什么不能直接删字段**：`usage_overview_service.rs:257 resolve_proxy_response_id()` 在
`upstream_response_id` 列为空时，会**回落到解析 `response_body`** 取上游 response id，
用于把本地会话条目与上游请求配对。全库 **31,188 / 92,673 行缺 `upstream_response_id`**，
删掉 `response_body` 会让这些行**永久丧失配对能力**（不可重建）。

**对照组**：`~/.ai-switch/logs/route-proxy-live-log.*` 是**另一套**日志，已自带轮转压缩，
6 个 `.jsonl.br` 段各 300–500 KB + 当前 28 MB，一共约 30 MB —— 有界，不是问题。问题只在 SQLite。

可选方向（**未执行**，等用户定）：1) `VACUUM`（仅回收页空洞，本库 `freelist=0`，几乎无效）；
2) 给 `usage_events` 加保留期 + 定期清理；3) 写入前对 `response_body` 做 BR/CR 压缩（SSE 文本压缩率极高）；
4) 有 `upstream_response_id` 的新行不再存 `response_body`（只保留缺失行的，缩小增量来源）。

### `usage_events.response_body` 膨胀：完整治理（同日 17:30 收尾）

**诊断回顾**：`~/.ai-switch/ai-switch.db` 337 MB，`usage_events` 92,673 行，
`metadata_json` 占 229.6 MiB（其中 `response_body` 一项 161.2 MiB，平均 1864 B、
上限 16384 B 系统性存满）。设计上「never pruned」。**不能直接删字段**：
`upstream_response_id` 为空的 31,188 行要靠解析 `response_body` 里的 SSE
取上游 response id 来配对会话，删了不可重建。

#### 落地方案：双键兼容 + 启动后台迁移 + 显式 VACUUM

**1. 双键兼容（无需 SQL 迁移即可双向兼容）**
- 新键 `response_body_br`（base64 of brotli quality 6 / lgwin 24），旧键 `response_body`（明文）。
- 写入端（两处）**只写新键**：`route_proxy_service.rs::route_proxy_response_body_metadata`
  （先截断 2 KiB/16 KiB → 压缩 → base64）与 `route_model_test_service.rs`（保留旧键，双写）。
- 常量 `ROUTE_PROXY_RESPONSE_BODY_ENCODED_KEY = "response_body_br"` /
  `ROUTE_PROXY_RESPONSE_BODY_KEY = "response_body"`，供读写两端共用。
- 读取端**两种都认，优先新键**：
  - Rust：`usage_overview_service.rs::proxy_response_body()` → `resolve_proxy_response_id()`
    回落链变成 `upstream_response_id` → 解压预览里解析 SSE id。
  - 前端：`src/lib/usageMetadata.ts` 的 `storedResponseBody(record)` + `decodeStoredBody()`。
    注意 `UsageOverviewPanel.tsx::RequestDetail` 要异步解码（`useEffect` + `useState`）。
- `brotli_codec.rs` 新增 `decode_stored_text()`（非 base64 形状原样返回；解不开也回落原文）
  与 `looks_like_base64()`（长度 ≥8、`%4==0`、仅 `[A-Za-z0-9+/=]`）。

**2. 启动后台迁移 `services/usage_history_compaction_service.rs`（新文件）**
- `migrate_stored_response_bodies()`：`LIKE '%"response_body"%' AND NOT LIKE '%"response_body_br"%'`
  → `ORDER BY created_at LIMIT 200` 分批、**每批各自事务**、批间 `yield_now()`。
  **幂等可续跑**：已有 `response_body_br` 的行天然跳过，重启即接着跑。
- `encode_row()` 有 **`(after < before).then_some(...)` 守卫**：短预览 base64 膨胀 4/3，
  压完反而更大（实测 67 B → 84 B，元数据 96 → 107），不划算就保留明文。
- `spawn_background_migration(pool)`：`START_DELAY = 10s`，避开 live-log 恢复与代理启动忙期。
  桌面端 `desktop.rs`（`live_log().persist_to()` 之后）与独立服务端 `server.rs`
  （`RouteRecoveryService::run_loop` 之后）**各自调用**。
- 一批里没有任何行可改写就 `break`（防不可解析行造成死循环）。

**3. VACUUM 做成显式动作（绝不进启动路径：独占锁 + 完整复制文件）**
- Rust `reclaimable_bytes()`（`page_size × freelist_count`）+ `vacuum()`。
- core 层 `core/usage_history.rs` → Tauri 命令 `get_usage_history_storage` /
  `compact_usage_history` → Web 派发（`web/handlers/mod.rs`）。
- ⚠️ **`compact_usage_history` 必须列入 `is_sensitive_command`**：会让桌面端卡几秒，
  配对手机不应触发全库重写。
- UI `components/settings/usage-storage-settings.tsx`：`WORTH_RECLAIMING_BYTES = 16 MiB`
  阈值、`!desktop` 返回 null、完成态/错误态；挂在 `SettingsScreen` 的 `AutostartSettings` 之后。

  → 浏览器端 brotli 解码用 `new DecompressionStream("brotli" as CompressionFormat)`，
  **走 `decompressor.writable.getWriter()` 显式写入 + `readable.getReader()` 收集**，别碰 Blob。
  TS 的 DOM `CompressionFormat` 未含 `brotli`，需 `as CompressionFormat` 断言。
- **`git stash` 会触发本仓库 git 元数据被外部删除**（见下方 git 恢复流程）。**避免使用 `git stash`。**

#### 干净副本对照的正确做法（detached worktree）
`git worktree add <path> HEAD --detach` 出来的副本**缺三个 gitignore 的构建产物**，
`cargo test` 会因为 custom build script 失败：
1. `src-tauri/binaries/ai-switch-tsnet-<triple>.exe`（sidecar）→ 「resource path ... doesn't exist」
2. `dist/`（前端产物）→ 「resource path `..\dist` doesn't exist」
3. 注意 `git worktree list` 显示的路径可能是 `D:/d/Repos/worktree/xxx`（**多了一层 `/d/`**），
   别照抄 `git worktree add` 时给的 `/d/...` 参数去 `cd`。
→ 从主树 `cp` 这两个进副本即可（另建议 `CARGO_TARGET_DIR=target-pristine` 避免共用 target）。

#### git 元数据被删的恢复流程（复现一次，已验证有效）

## 收尾：flaky 根因第二层 + 「压缩后还能不能搜索」核查

### flaky 复发（修过 created_at 后仍 1/50）
- 现象：修完「流内 created_at 同源」后 `the_streamed_transform_matches_the_buffered_one_byte_for_byte` 仍 1/50 挂。

  是**两条路径各建一次 `ChatStreamBridge` state、各读一次 `Utc::now()`**。
- 修法：给 `chat_sse` fixture 每个 chunk 写死 `"created":1700000000`（真实 upstream 每帧都带）。
  两条路径都从 `capture_envelope` 读 `created`（`responses_chat.rs:416`），有值就不回落时钟。

# 旧账号池收敛启动故障修复设计

## 目标与证据

v0.18.0 在窗口建立前执行 `open_migrated_pool`，其中旧账号池收敛删除了仍被 SaaS 数据引用的旧分组，导致 SQLite 787 外键错误并退出。本机 SQL 迁移已经提交；三个 Claude 旧组仍有模型或同步记录，84 个账号尚在。目标是恢复升级迁移，同时无损保留所有账号、成员、定价、同步与账务数据。

## 推荐方案

补齐 `RoutePoolRepository::converge_legacy_pool_groups` 的引用保护集合：逐一检测 `saas_api_keys`、`saas_group_settings`、`saas_group_models`、`saas_group_model_sync`、`saas_billing_reservations`、`saas_usage_hourly` 是否存在，只读取存在的表，合并去重 `group_id`。现有事务中成员搬迁与分组删除共用完整集合。被引用旧组和其成员原地保留；无引用旧组沿用现有收敛规则；成功后清除标记。

只有这一种无损且最小的方案：关闭外键、删除引用行或直接清标记都会掩盖数据关系；把全部账务迁移到 codex 会改变历史归属，超出修复需要。方案由代理推荐，用户批准了对应实现计划。

## 约束

- 不修改已发布 SQL，不关闭外键，不删除账号或历史，不改价格和账务归属。
- 保持核心启动顺序和既有交易、幂等行为。
- 保持 `main`，不建分支，不修改其它会话的文档或本地开发配置。
- 所有 Cargo 验证复用 `src-tauri/target-codex`。
- 本阶段不修改真实数据库、覆盖安装目录或发布新版本。用户另行确认后才执行这些操作。

## 验收

新增回归须先在旧实现下报外键错误。覆盖六表独立引用、三类旧视图、无 SaaS、部分 SaaS schema、无引用组收敛、两次启动和完整升级入口。修复后外键检查为空；引用表内容、账号和成员不丢失；真实数据库只读备份至隔离目录，使用生产迁移入口验证副本启动与第二次启动。

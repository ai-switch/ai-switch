# 搭一个不会断的算力池

**目标**：主力号被限流或断线时，客户端无感知地落到备用号；一段时间之后主力号能自己回到池子里。

**你需要**：至少两个同平台的可用账号（第三个可选）；已完成 [跑通第一条请求](./first-request)。

**验收标准**：人为让主力号失败后，请求列表里下一条请求的「账号名」变成备用号，且客户端没有报错；主力号恢复后能重新被选中。

## 先理解三条调度规则

选号不是「随机挑一个」，顺序固定：

1. **SQL 层过滤**：在池内、启用、未归档、`status = ok`、配额字段为空或大于 0。
2. **平台能力 + 模型过滤**：请求的模型必须有账号支持，否则 `route_pool.model_unmatched`。
3. **冷却分桶**：按优先级分组轮转，跳过冷却 / 暂停 / 异常的对象。

优先级是**严格分层**的：优先级 1 的账号全部不可用，才会用到优先级 2。同一层内按列表顺序轮转（算力池视图里可以拖动行改顺序），并发上限是硬限制，跑满的账号直接跳过。

::: warning 每个平台一个池
Codex、Claude Code、Gemini CLI 各自有独立的池和独立的代理 key。这篇教程里的三层结构要在**同一个平台**里搭，跨平台不会互相兜底。
:::

## 第 1 步：把账号分成三层

在算力池视图里逐个「编辑账号」→「高级」分区，设 **路由优先级**（1–5，默认 3，数字越小越优先）与 **最大并发数**（界面默认 5，最小 1）：

| 角色 | 优先级 | 并发上限建议 | 说明 |
| --- | --- | --- | --- |
| 主力：便宜、稳定、额度多 | **1** | 按上游许可，官方账号可设 1–2 | 平时所有流量都在这里 |
| 备用：价格略高或额度较少 | **3** | 同主力 | 主力全挂才启用 |
| 兜底：贵、只在紧急时用 | **5** | 1 | 只用来保证不中断 |

同一层放多个账号可以做层内轮转，把并发压力摊开。拖动行调整的是**同层**轮转起点，不会越过优先级分层。

> ✅ **检查点**：算力池列表按优先级显示 1 / 3 / 5 三层，三个账号状态都是「正常」。

::: tip 只有一个账号能先做吗
能。先把一个账号配好失败策略与自动恢复，等有第二个账号时再补优先级。但「故障转移」本身需要至少两个候选，单账号时它的效果只是同号重试。
:::

## 第 2 步：配好失败策略

编辑账号 →「高级」→「故障处理」→「失败处理策略」。默认值适用于大多数场景，但要知道它们分别管什么：

| 字段 | 默认 | 作用 |
| --- | --- | --- |
| `retry_count` | 2 | 失败后**同号再试**几次，用完才换号 |
| `retry_interval_ms` | 200 | 同号重试的等待间隔（毫秒） |
| `semantic_error_threshold` | 10 | 同一模型的同一种语义失败连击多少次后把模型置为 `error` |
| `failover_enabled` | `true` | 失败后是否切到池内其他账号 |
| `stream_continue_enabled` | `false` | 流式响应中途断流时是否自动续写（**一次完整计费请求**） |
| **启用失败冷却** | **默认关闭** | 关着时只累加失败次数，不写冷却时间戳 |
| 失败冷却（秒） | 10 | 开启后每次瞬时失败等这么久，范围 1–86400 |

**建议**：主力号打开「启用失败冷却」，先按 10 秒用；备用号保持默认即可。冷却时长是固定的、不阶梯增长——一次抖动的代价是秒级而不是分钟级。

::: warning 401 / 403 永不同号重试
鉴权失败重试只会更快触发上游风控，代理直接记失败并换号。所以「key 填错」这类问题会很快把所有账号都试一遍，别拿它当故障演练。
:::

## 第 3 步：配自动恢复

同一个「故障处理」分区里的「自动恢复」有三种模式：

| 模式 | 行为 | 适合 |
| --- | --- | --- |
| `off`（默认） | 不做任何自动恢复 | 想完全手工控制 |
| `scheduled` | 每天固定时刻（本地时区 `HH:MM`）**无条件**重新激活 | 上游按自然日重置额度，把时刻设在重置之后一小会儿 |
| `healthcheck` | 按间隔跑一次真实模型连通性测试，**测通了才恢复**，默认 30 分钟 | 限流窗口不确定 |

调度器每 30 秒跑一个 tick，跨零点、机器休眠几天都能正确触发。推荐组合：**主力号 `healthcheck`（15–30 分钟），备用号 `scheduled`（额度重置后），兜底号 `off`**——探测会消耗一点配额并在统计里留下一条请求事件，兜底号没必要常探。

::: details 两层冷却：为什么徽章有两个
冷却默认是**模型级**的：中转站常常只对某一个模型限流，把整个账号打成冷却会误伤同号上健康的其他模型。只有 `refresh`、`request_build`、`transport`、401/403、配额耗尽、权限不足这几类才直接记到**账号级**；当一个账号的全部可服务模型都不可用时，会升级成账号级冷却。

界面上因此有两个语义不重叠的徽章：`冷却 N 秒`（整号退避）和 `模型 N 不可用`（部分模型冷却 / 异常 / 暂停）。悬停后者能看逐模型明细。
:::

## 第 4 步：故障演练（最重要的一步）

不要等真出事才发现没配好。做一次可控演练：

1. 点 **✈** 发一次真实生成测试，记下统计里命中的账号名（应当是优先级 1 的主力号）。
2. 编辑主力号，把 **Base URL 临时改成** `http://127.0.0.1:9/v1`（一个必然连不上的地址），保存。这会制造一次 `transport` 瞬时失败，不会真的消耗上游配额。
3. 连续发起两三次普通请求（CLI 里问一句话即可，别用 ✈ 测试，测试事件会混进统计）。
4. 打开「统计」视图看请求列表的**账号名**列。

> ✅ **检查点**：后续请求落到优先级 3 的备用号，客户端全程没有报错；主力号行出现 `错误 N 次` 状态标签。

5. 把主力号 Base URL 改回来。如果配了 `healthcheck`，等一个探测间隔（或直接在账号上点一次 ✈ 显式测试，成功即完整恢复）；如果配了 `scheduled`，也可以点 `冷却 N 秒` 徽章 →「立即解除冷却」手工恢复。
6. 再发一条请求，确认账号名回到主力号。

::: tip 手动恢复不消耗配额的三个入口
- 账号行 `冷却 N 秒` 徽章 → 改剩余秒数或「立即解除冷却」（只清账号级）
- 编辑抽屉「故障处理」→「模型状态」里逐模型点 `解除`（清模型级冷却与异常）
- 针对单个账号点一次 ✈ 模型连通性测试，成功即恢复账号（会消耗一次配额）
:::

## 第 5 步：看懂状态标签与错误码

账号行的标签是排错的第一现场：

| 界面显示 | 含义 |
| --- | --- |
| `错误 N 次` | 连续瞬时失败次数；下一次请求成功自动清零 |
| `冷却 N 秒` | 账号级冷却剩余时间，可点击调整或立即解除 |
| `模型 N 不可用` | 冷却未过期 + `error` + `paused` 的模型数量，悬停看明细 |
| `已失效` / `异常` / `暂停` | 状态分别是 `revoked` / `error` / `paused`，不会被自动覆盖 |

客户端侧的错误码（都在 HTTP **502** 的错误体 `error.code` 里，代理不透传上游状态码）：

| 错误码 | 意思 | 处置 |
| --- | --- | --- |
| `No enabled route credentials in pool` | 池内没有可用账号 | 检查是否全被禁用 / 归档 / 状态非 `ok` |
| `route_pool.model_unmatched` | 没有任何账号映射这个模型 | 补模型映射 |
| `route_pool.model_unavailable` | 有账号支持，但该模型全被暂停或判异常 | 去「模型状态」里解除 |
| `route_pool.concurrency_exhausted` | 所有账号并发占满 | 调高「最大并发数」或加账号 |
| `route_pool.access_disabled` | 独立服务器里关掉了算力池路由接入 | 在面板里重新开启 |

::: warning 冷却不等于请求失败
如果筛完一个可用账号都不剩，调度器会**挑出最快恢复的那个冷却账号试一次**，而不是直接报错。这是有意的取舍：退避时长本身是估算，上游可能已经恢复了。但 `paused` 与 `error` 是裁决，硬排除到底，不参与兜底探测。
:::

## 失败分类速查

知道上游返回什么会被怎么处理，才能判断演练结果对不对：

| 类别 | 触发 | 后果 |
| --- | --- | --- |
| 瞬时（Transient） | 408 / 401 / 403 / 429 / 任意 5xx / 连接失败、DNS、TLS、超时 | 同号重试 → 记失败 → 冷却 → 换号 |
| 永久（Permanent） | `invalid_grant`、`token has been revoked` 等凭据作废文本 | 状态直接写 `revoked`，不设退避，**永不参与自动恢复** |
| 不算失败（None） | 400 参数错误、404 路径不存在 | 不累加失败计数，账号状态不动 |
| 语义失败 | HTTP 200 但响应体是失败；SSE 在完成事件前断流 | 标记失败并按指纹累计连击 |
| 配额耗尽 / 缺 scope | 固定文本或 `error.code` 命中 | 阈值硬编码为 1，**一次就置 `error`** |

出站还有两个超时上限：连接超时 20 秒、读取间隔超时 180 秒（每读到数据就重置）。上游「连上了但一个字节都不发」也会被变成一次可换号的失败，客户端不会无限期挂着。

## 长期运行的三个提醒

- **成功会清账，但不对称**：一次成功转发会清空账号级全部失败痕迹，模型级**只删本次命中的那个模型**，绝不动兄弟模型。测通 A 模型不代表 B 模型也好了。
- **归档会让历史消失**：统计查询 `INNER JOIN` 未归档账号，归档一个账号后它的历史事件立刻从统计里消失，取消归档又回来。对账前别随手归档。
- **`paused` 是用户意志**：定时任务与成功清账都不会推翻手动暂停，只能你自己解除。
